# 工程实践

AIHelper 需要让模型推理、人工标注、交互复核和质量报告共享可追溯的数据。工程重点既包括跨入口和图源的一致性，也包括指标口径、标注身份与独立工具之间的衔接。

## 关键问题与取舍

| 问题 | 设计选择 | 收益 |
| :--- | :--- | :--- |
| GUI 与批处理结果逐渐不同 | 使用同一请求契约和流水线服务 | 默认值、阶段顺序和失败行为只有一个来源 |
| 大图切块后坐标容易漂移 | 保留图源比例、偏移、旋转四点和父子身份 | 显示、后处理与评分共享同一坐标依据 |
| 后台推理影响界面稳定性 | 后台只发布事件，主线程负责控件更新 | 降低冻结、竞态和跨线程访问风险 |
| GPU 模型加载成本高 | 明确模型准备、会话池与释放边界 | 批量任务可复用资源，同时避免无限驻留 |
| 回归差异被“更新标准答案”掩盖 | 基线只读，差异强制失败并保存报告 | 每一次通过都有可解释的验证依据 |
| 调试文件污染正式输出 | 调试产物与业务输出分区，但保留稳定发布路径 | 兼顾可追溯性与下游兼容性 |
| 修改父框后子结构和 OCR 失去关联 | 使用稳定身份与父子引用，保存时校验和重新绑定 | 标注、结果和评分能够对应到同一对象 |
| 浏览器旧页面覆盖新标注 | revision 冲突检查、原子保存、备份和联合事务 | 让保存冲突显式可见 |
| 检出问题与分类问题混在一个分数中 | Stage1 检测与 CLS 独立评价，记录 GT／预测框来源 | 能区分漏检、错分和分类失败 |
| 整体均值掩盖局部退化 | 按程序、阶段、元件类别汇总，并展示最差程序与误差分布 | 更快定位需要复核的样本 |
| 汇总后无法解释某个分数 | 保留原始记录和源报告链接，提供图像错误定位 | 从版本指标逐步追到具体目标 |

## 报告工具的职责划分

单程序评测负责计算匹配和指标；`综合评分.py` 读取既有评分记录；HTML 和 Excel 生成器负责组织展示。重新汇总已有数据无需加载推理模型，HTML 模式也可独立于 Excel 依赖运行。

汇总时各阶段保留独立口径，不将检测、分类和 OCR 混成一个总分。开发诊断按有效匹配框汇总几何指标，同时展示程序层面的差异。DIR 与一级 GT 的角度比较仅作诊断，不包装成准确率。

## 以第一处差异为目标

单看最终检测数量无法判断两套流程是否真正一致。AIHelper 将排查顺序固定为：

1. 输入图像和读取方式；
2. 预处理后的模型张量；
3. 原始模型输出；
4. 各步过滤后的对象集合；
5. 坐标、类别、文字和父子关系；
6. 最终结果树与发布报告。

这种数据流视角能把“结果不一样”缩小为一个明确阶段和一组可复核证据。

## 验证原则

- 默认入口测试优先于只覆盖显式开关的函数测试。
- 阈值边界同时覆盖小于、等于和大于三种情况。
- 缓存命中与重新计算必须产生等价业务结果。
- 空结果、取消、回退和失败路径与成功路径同样需要验证。
- 源码级回归通过与真实设备运行一致是不同结论，分别记录。

## 可维护性

项目通过稳定公开入口、依赖方向约束、结构化事件和不可变输出约定控制变化范围。新增阶段或入口时，优先扩展应用契约，而不是绕过流水线直接调用内部模块。

便携标注包通过冻结输入与预测支持跨电脑交接；外部数据采集通过子进程和 JSON 协议调用。独立工具及其能力边界见[功能全景](features.md)。
