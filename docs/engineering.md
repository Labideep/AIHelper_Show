# 工程实践

AIHelper 的难点不只是运行多个视觉模型，而是确保不同入口、不同图源和不同运行时条件下，阶段之间仍保持一致且可解释的行为。

## 关键问题与取舍

| 问题 | 设计选择 | 收益 |
| :--- | :--- | :--- |
| GUI 与批处理结果逐渐不同 | 使用同一请求契约和流水线服务 | 默认值、阶段顺序和失败行为只有一个来源 |
| 大图切块后坐标容易漂移 | 保留图源比例、偏移、旋转四点和父子身份 | 显示、后处理与评分共享同一坐标依据 |
| 后台推理影响界面稳定性 | 后台只发布事件，主线程负责控件更新 | 降低冻结、竞态和跨线程访问风险 |
| GPU 模型加载成本高 | 明确模型准备、会话池与释放边界 | 批量任务可复用资源，同时避免无限驻留 |
| 回归差异被“更新标准答案”掩盖 | 基线只读，差异强制失败并保存报告 | 每一次通过都有可解释的验证依据 |
| 调试文件污染正式输出 | 调试产物与业务输出分区，但保留稳定发布路径 | 兼顾可追溯性与下游兼容性 |

## 以第一处差异为目标

单看最终检测数量无法判断两套流程是否真正一致。AIHelper 将排查顺序固定为：

1. 输入图像和读取方式；
2. 预处理后的模型张量；
3. 原始模型输出；
4. 各步过滤后的对象集合；
5. 坐标、类别、文字和父子关系；
6. 最终结果树与发布报告。

这种数据流视角能把“结果不一样”缩小为一个明确阶段和一组可复核证据。

## 验证原则

- 默认入口测试优先于只覆盖显式开关的函数测试。
- 阈值边界同时覆盖小于、等于和大于三种情况。
- 缓存命中与重新计算必须产生等价业务结果。
- 空结果、取消、回退和失败路径与成功路径同样需要验证。
- 源码级回归通过与真实设备运行一致是不同结论，分别记录。

## 可维护性

项目通过稳定公开入口、依赖方向约束、结构化事件和不可变输出约定控制变化范围。新增阶段或入口时，优先扩展应用契约，而不是绕过流水线直接调用内部模块。
