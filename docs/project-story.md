# 项目故事

## 背景

AOI 算法开发涉及多种图源、多个模型、人工标注与大量结果复核。一次推理结束后，还需要回答：哪些目标漏检了，哪些类别分错了，框的几何是否合适，新版本在哪些程序上退化，以及如何将样本交给标注或数据采集流程。

## 目标

AIHelper 将这些工作连接成可追溯的本地工具链：桌面端调试模型，浏览器维护 GT 与复核结果，评分模块量化质量，独立报告工具比较版本，便携任务包与 JSON 接口支持数据交接。

## 一次典型的使用过程

1. 在桌面加载程序并运行所需阶段，或直接导入已保存的结果。
2. 在浏览器标注元件、子结构和 OCR，维护明确的父子关联与排除区。
3. 评估已有结果，在 HTML 报告中筛选错误并定位到图像目标。
4. 批量运行多个程序，用综合评分工具生成 Excel、版本驾驶舱和开发调试指标页。
5. 从类别或程序的异常指标下钻到源报告，决定下一步需要复核的输入、模型或标注。

需要他人参与标注时，可交接便携标注包；需要外部采集项目调用时，可使用子进程与 JSON 接口。各步骤按已有数据选择，不要求每次从头执行。

## 主要挑战

- 多阶段模型之间存在父子关系和坐标依赖。
- 大图切块、缩放、旋转和透视裁切会累积几何误差。
- GUI、批处理和独立调用容易形成不同默认行为。
- GPU 模型加载、并发和释放会影响吞吐及稳定性。
- 生产语义与纯模型结果并不完全等价，需要明确边界。
- 编辑一级标注时，二级和 OCR 的稳定身份与关联仍需有效。
- 多程序平均分可能掩盖某个元件类别的退化，需要可下钻的分组指标。

## 解决思路

项目用统一应用流水线承接推理入口，通过结构化上下文传递阶段证据；用稳定的板级坐标和父子身份连接结果与标注；用独立评测和报告工具连接单框诊断、程序质量与版本表现。评分读取人工维护的 GT，回归差异保留报告，不自动修改标准答案。

## 适合在面试中展开的内容

1. 如何把遗留 GUI 调用收敛到统一应用服务；
2. 如何保证旋转框跨缩放和裁切后的坐标一致性；
3. 如何设计后台任务事件，避免界面线程竞态；
4. 如何区分模型输出、后处理结果和生产软件语义；
5. 如何建立不会自动掩盖差异的回归验证机制；
6. 如何设计有父子约束、版本冲突检查和便携交接的标注工具；
7. 如何把单框评分转为可定位问题的版本、程序与元件类别报告。

## 展示边界

公开仓库只描述问题、设计与结果。具体业务规则、模型资产、生产数据、内部运行参数和完整实现保留在私有环境中，可在授权场景下进行代码走读或现场演示。
