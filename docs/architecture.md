# 公开架构设计

本文只描述可以公开的设计原则和组件关系，不包含业务源码、生产参数、模型信息或内部系统地址。

## 设计目标

AIHelper 需要同时服务交互式调试和批量回归。两种入口如果各自编排模型，很容易在默认值、执行顺序、错误处理和结果格式上产生偏差。因此系统将入口与执行逻辑分离：入口负责表达意图，应用层负责验证并执行有序流水线。

![AIHelper architecture](../assets/architecture.svg)

## 分层职责

| 层级 | 主要职责 | 边界 |
| :--- | :--- | :--- |
| Interface | GUI、批量任务和独立推理入口 | 不复制业务流程，不直接管理模型生命周期 |
| Application | 请求验证、阶段编排、事件、取消和失败报告 | 统一所有入口的运行语义 |
| Vision modules | 检测、分类、方向、子结构与 OCR | 只通过明确上下文交换阶段结果 |
| Validation | 标准答案、指标、差异和报告 | 基线只读，差异不可静默忽略 |
| Infrastructure | 图源、程序数据、状态、锁和输出 | 隔离文件系统与运行环境细节 |

## 核心数据流

![AIHelper pipeline](../assets/pipeline.svg)

每次运行都带有独立身份，并记录其输入来源、启用阶段和模型角色。阶段之间传递结构化结果，而不是从界面临时状态推断业务数据。旋转框和子结构结果最终统一恢复到板级坐标空间，以便显示、评分和导出使用同一几何定义。

## 并发模型

- 耗时图像处理和推理在后台任务中执行。
- 后台任务只发布不可变事件，不直接修改界面控件。
- 界面线程按顺序消费事件并更新状态。
- 运行状态和输出发布采用并发安全写入，避免多个入口互相覆盖。

## 失败语义

流水线把失败视为业务结果的一部分：阶段错误会终止依赖它的后续阶段，同时保留已经确认的运行身份、阶段信息和诊断报告。基线验证发现差异时同样返回失败，而不是修改标准答案使本次运行通过。

## 兼容策略

公开入口和输出结构属于稳定契约；兼容层只负责适配历史调用，不承载新的业务规则。新能力首先进入统一流水线，再由需要的入口调用，避免长期形成多套实现。
